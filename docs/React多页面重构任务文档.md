# 秘仪室 React 多页面重构任务文档

## 1. 背景

当前项目的前端架构为：

- 原生 HTML + CSS + JavaScript
- 多页面结构：`/`、`/kp-site/`、`/player/`
- 页面通过独立的脚本文件直接操作 DOM
- 服务端使用 Node.js 原生 HTTP 服务提供静态资源、API 和 SSE

当前这套结构在项目早期足够轻便，但随着需求增加，前端复杂度已经明显提升，尤其在以下方向：

- KP 控制台正在从“展示切换面板”演进为“舞台编辑器”
- 文本、图片、模板、字段可见性会逐渐变多
- KP 端和玩家端开始共享越来越多的数据结构和展示逻辑
- 后续还会引入编辑模式、演出模式、模板化和更完整的房间配置

这意味着当前“原生 DOM + 分散脚本”的维护成本会越来越高。

## 2. 重构目标

将现有原生前端逐步迁移为：

- **React**
- **TypeScript**
- **Vite**
- **多页面 / 多入口结构**

重构目标不是立刻大改后端，而是在保留现有 Node API 与 SSE 协议的前提下，先把前端工程层升级到更适合长期维护的结构。

## 3. 为什么选择 React 多页面，而不是单页 SPA

本项目更适合 React 多页面，而不是单页 SPA，原因如下：

### 3.1 当前 URL 结构天然就是多页面

当前用户路径已经非常明确：

- `/`：平台首页
- `/kp-site/`：KP 控制台
- `/player/`：玩家只读舞台

这些页面职责差异很大，保留多页面结构更贴近现有业务心智。

### 3.2 KP、玩家、首页属于三种不同产品界面

- 首页偏入口页
- KP 页偏后台 / 编辑器
- 玩家页偏只读舞台

它们不需要强耦合成一个单页路由系统。

### 3.3 迁移成本更低

如果采用多入口 React：

- 可以逐页替换
- 可以保持原 URL 不变
- 可以逐步复用共享模块
- 不必先引入复杂的前端路由和客户端导航机制

### 3.4 玩家页应尽量轻

玩家页是只读舞台，不需要承载大量编辑器逻辑。多页面结构可以让玩家页保持更轻、更清晰。

## 4. 重构原则

### 4.1 后端先不大动

第一阶段只重构前端工程组织方式，不优先改动：

- 房间 API 结构
- SSE 通道协议
- Node 服务入口

### 4.2 先迁页面层，再整理业务层

先把页面迁到 React，再逐步抽离：

- API 层
- 房间状态层
- 舞台展示组件
- 模板与覆盖模型

### 4.3 保持 URL 稳定

重构后应继续保留：

- `/`
- `/kp-site/`
- `/player/`

避免影响已有链接结构和房间使用方式。

### 4.4 组件共享优先于页面耦合

KP 端和玩家端虽然是两个页面，但会共享：

- 舞台背景组件
- NPC 展示组件
- 素材展示组件
- 房间数据类型
- API 调用逻辑

因此要通过共享模块复用，而不是靠一个大页面内部切模式。

## 5. 目标技术栈

建议目标栈如下：

- Vite
- React
- TypeScript
- 原生 CSS 或 CSS Modules

本轮不强制引入：

- Next.js
- React Router
- Zustand / Redux
- Tailwind
- UI 组件库

理由：

- 项目规模还没有大到必须先上这些工具
- 多入口 React 本身已经能显著改善结构
- 先把数据模型、组件边界和编辑流程跑顺更重要

## 6. 目标目录结构

建议迁移后的目录结构如下：

```text
src/
  pages/
    home/
      main.tsx
      App.tsx
    kp/
      main.tsx
      App.tsx
    player/
      main.tsx
      App.tsx

  shared/
    api/
    components/
    room/
    stage/
    types/
    utils/

  styles/
    tokens.css
    base.css
```

同时保留：

```text
server.mjs
assets/
docs/
```

## 7. 推荐模块拆分

### 7.1 `shared/types`

负责统一数据类型定义，例如：

- `RoomState`
- `StageState`
- `RoomMeta`
- `LocationItem`
- `NpcItem`
- `MaterialItem`
- `PlayerSlot`
- `CustomImages`
- `CustomText`

### 7.2 `shared/api`

负责前后端通信：

- `createRoom`
- `getRoomState`
- `pushRoomState`
- `uploadRoomAsset`
- `subscribeRoomEvents`

### 7.3 `shared/stage`

负责舞台展示逻辑：

- `StageBackground`
- `NpcLayer`
- `MaterialLayer`
- `PlayerLayer`
- `ConnectionBadge`

### 7.4 `shared/room`

负责房间状态管理与数据整形：

- 默认值
- 自定义覆盖合并
- 房间状态归一化
- 公私字段分层

### 7.5 `pages/home`

负责：

- 创建房间
- 加入房间
- 后续的“从模板创建”“创建空白房间”

### 7.6 `pages/kp`

负责：

- 房间连接
- 演出模式
- 编辑模式
- 房间同步
- 上传图片
- 后续文本编辑

### 7.7 `pages/player`

负责：

- 连接房间
- 接收 SSE
- 渲染玩家只读舞台

## 8. 页面职责划分

### 8.1 首页

职责：

- 快速进入工作流
- 减少解释性内容
- 提供清晰的创建/加入入口

### 8.2 KP 页面

职责：

- 管理房间当前舞台状态
- 提供编辑与演出控制能力
- 同时承担配置与实时预览

### 8.3 玩家页面

职责：

- 展示当前公开舞台内容
- 保持画面沉浸和只读
- 不承载后台逻辑

## 9. 状态管理策略

第一阶段不建议一开始引入外部状态管理库。

建议优先采用：

- 组件内 `useState`
- 页面级 `useReducer`
- 自定义 hooks

适合当前阶段的 hooks 包括：

- `useRoomConnection`
- `useRoomState`
- `useStagePreview`
- `useAssetUpload`

等到文本编辑、模板编辑、复杂表单和跨区块同步明显变复杂后，再评估是否引入 Zustand。

## 10. 样式策略

建议保留当前视觉方向，但重构样式组织：

- 提取基础 token
- 提取舞台层通用样式
- 将页面级样式和共享样式分离

建议结构：

- `tokens.css`：颜色、阴影、间距、字体尺寸
- `base.css`：全局 reset、基础标签样式
- 页面或组件局部样式：跟随模块放置

本轮不强制迁移到 CSS-in-JS。

## 11. 与现有后端的衔接方式

第一阶段应继续兼容现有：

- `/api/rooms`
- `/api/rooms/:room/state`
- `/api/rooms/:room/events`
- `/api/rooms/:room/assets`

即：

- 前端工程结构升级
- 后端协议暂不大改

这样可以把风险集中在前端，不让架构迁移和业务重构同时爆炸。

## 12. 实施阶段

### 阶段 1：工程底座建立

目标：

- 引入 Vite + React + TypeScript
- 配置多入口构建
- 保持现有后端可继续服务构建产物

交付：

- React 多入口脚手架
- `src/pages/home`
- `src/pages/kp`
- `src/pages/player`
- 基础类型和 API 层

### 阶段 2：首页迁移

目标：

- 将平台首页迁移到 React
- 功能保持不变

交付：

- 创建房间
- 加入房间
- 基础错误提示

### 阶段 3：玩家页迁移

目标：

- 将玩家页迁移到 React
- 保持 SSE 实时同步和只读舞台能力

交付：

- 背景展示
- NPC 展示
- 素材展示
- 连接状态
- 错误态

### 阶段 4：KP 页迁移

目标：

- 将 KP 控制台迁移到 React
- 保持现有切换、上传、同步能力

交付：

- 地点/NPC/素材/玩家切换
- 图片上传
- 房间状态同步
- KP 备注显示

### 阶段 5：编辑器能力承接

目标：

- 在 React 结构上承接“文本可编辑”“编辑模式”“模板化”

交付：

- 文本编辑表单
- 更清晰的页面分区
- 数据模型升级

## 13. 验收标准

完成 React 重构第一阶段后，应满足：

- 项目可以通过 `npm start` 提供页面
- 首页、KP 页、玩家页都由 React 渲染
- 原有 URL 不变
- 原有房间 API 可继续使用
- SSE 实时同步继续工作
- 图片上传功能不退化
- 现有视觉风格不发生明显退化

## 14. 风险与注意事项

### 14.1 不要在第一阶段同时重写后端协议

否则容易出现：

- 前端重构问题
- API 改动问题
- SSE 问题

三者耦合，定位困难。

### 14.2 不要直接上单页大路由

否则容易把：

- 首页
- KP 页
- 玩家页

这三种职责完全不同的页面绑死在一起。

### 14.3 不要过早引入太多库

本项目当前真正的核心不是“库不够多”，而是：

- 数据结构需要清晰
- 页面职责需要清晰
- KP 与玩家的边界需要清晰

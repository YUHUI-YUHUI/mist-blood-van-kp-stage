# 秘仪室 React 多页面重构开发清单

## 1. 文档目的

本文件用于把以下两份任务文档转成可执行开发清单：

- [舞台编辑器改造任务文档](</Users/yuhui/Documents/coc kp platform/docs/舞台编辑器改造任务文档.md>)
- [React多页面重构任务文档](</Users/yuhui/Documents/coc kp platform/docs/React多页面重构任务文档.md>)

本清单重点解决三件事：

- 明确先做什么，后做什么
- 将“React 多页面重构”与“舞台编辑器能力演进”对齐
- 给出每个阶段的交付物、验收点和风险控制

## 2. 总体策略

### 2.1 先重构壳，再承接能力

顺序固定为：

1. 搭 React 多入口工程底座
2. 迁首页
3. 迁玩家页
4. 迁 KP 页
5. 承接文本可编辑与编辑模式

### 2.2 不同时重写前后端协议

在 React 底座建立阶段，不同步重写：

- 房间 API
- SSE 协议
- 资源上传协议

所有 React 页面先复用现有 `server.mjs` 提供的接口。

### 2.3 先保留页面 URL

迁移阶段必须保证以下路径不变：

- `/`
- `/kp-site/`
- `/player/`

### 2.4 迁移过程中允许“新旧并存”

在未完全替换前，允许仓库中同时存在：

- 旧版原生页面代码
- 新版 React 页面代码

但每一阶段结束时，必须明确：

- 哪个页面已经切到 React
- 哪个页面仍由原生代码承担

## 10. 推荐首个开发批次

建议接下来优先完成一个最小但完整的批次：

### 批次 1

- [ ] 建立 Vite + React + TypeScript 底座
- [ ] 初始化多入口
- [ ] 初始化 `shared/types` 与 `shared/api`
- [ ] 迁移首页到 React

原因：

- 首页复杂度最低
- 可以先验证多入口构建链路
- 不会立刻碰最复杂的 KP 编辑器问题

## 11. 风险控制清单

- [ ] 不在阶段 A 同时重写后端协议
- [ ] 不在阶段 A 引入多余状态库
- [ ] 不在阶段 B 就急着迁 KP 编辑器能力
- [ ] 保持旧逻辑可回退，直到对应页面的新版本稳定
- [ ] 每完成一个页面迁移，就做一次本地联调验证

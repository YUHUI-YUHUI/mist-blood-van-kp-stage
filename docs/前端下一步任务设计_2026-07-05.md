# 秘仪室前端下一步任务设计（2026-07-05）

## 1. 目标

基于本轮联调结果，下一阶段的目标不是继续堆新功能，而是先把“可开房、可切换、可同步、可在玩家端正确展示”这条主链路修稳。

本轮建议按下面的顺序推进：

1. 修复内置模板房间同步
2. 补齐玩家端玩家席位展示
3. 修正移动端玩家页信息遮挡
4. 梳理 KP 专用 / 玩家可见内容的展示边界
5. 补自动化回归用例

---

## 2. 任务分级

### 阶段 A：阻塞修复

#### A1. 修复内置模板房间状态同步

优先级：`P0`

目标：

- 内置模板房间创建后，KP 任意切换地点 / NPC / 素材 / 玩家席位，都能正常推送到服务端。

涉及文件：

- [server.mjs](/Users/yuhui/Documents/coc%20kp%20platform/server.mjs:495)
- [src/shared/templates/index.ts](/Users/yuhui/Documents/coc%20kp%20platform/src/shared/templates/index.ts:223)
- [src/shared/room/state.ts](/Users/yuhui/Documents/coc%20kp%20platform/src/shared/room/state.ts:54)

建议实现方向：

- 服务端引入“完整模板解析”能力，不再依赖 `templateDefaults(...)`。
- 把模板 ID -> 完整模板对象的解析抽成统一入口。
- 明确服务端用于校验 `locationId / npcId / materialId / playerIds` 的数据源。

验收标准：

- 创建“雾中献血车”房间后，KP 选中 NPC，顶部状态不会出现异常。
- `POST /api/rooms/:room/state` 返回 `200`。
- 玩家端刷新后能看到对应变化。

---

#### A2. 给同步失败增加用户态错误兜底

优先级：`P1`

目标：

- 即使底层抛异常，KP 页也不要直接展示原始 JS 报错。

涉及文件：

- [src/shared/room/useKpRoom.ts](/Users/yuhui/Documents/coc%20kp%20platform/src/shared/room/useKpRoom.ts:74)

建议实现方向：

- `pushLatestRoomState()` 中把用户可见文案和原始异常分开。
- 用户可见文案例如：
  - “舞台同步失败，请稍后重试”
  - “当前房间模板数据异常，请重新建房或联系维护者”

验收标准：

- 人工制造一次同步失败时，页面不再显示原始异常字符串。

### 阶段 B：玩家端可见性修复

#### B1. 玩家端补齐在场玩家展示

优先级：`P1`

目标：

- KP 端选中的玩家席位，玩家端也能看到。

涉及文件：

- [src/shared/stage/PlayerStage.tsx](/Users/yuhui/Documents/coc%20kp%20platform/src/shared/stage/PlayerStage.tsx:26)
- [src/shared/stage/KpStagePreview.tsx](/Users/yuhui/Documents/coc%20kp%20platform/src/shared/stage/KpStagePreview.tsx:73)
- [src/shared/stage/content.ts](/Users/yuhui/Documents/coc%20kp%20platform/src/shared/stage/content.ts:59)
- [src/shared/stage/stage.css](/Users/yuhui/Documents/coc%20kp%20platform/src/shared/stage/stage.css:161)

建议实现方向：

- 为玩家端补一个精简版 `player-side` 区域。
- 尽量复用 KP 预览页的玩家卡样式和数据解析。
- 明确玩家端是否需要展示：
  - 玩家姓名
  - 身份描述
  - 头像 / 首字母

验收标准：

- 自定义模板房间中选中玩家席位后，玩家端可见对应卡片。
- 玩家端正文中能看到玩家名称或席位信息，而不是只在 KP 预览里可见。

目标：

优先级：`P3`

目标：

- 玩家端首屏的信息优先级更清晰，避免“标题、提示语、状态、地点卡片”互相抢位置。

  - 当前地点

---

#### D2. 增加最小化 KP -> 玩家联调用例

优先级：`P2`

目标：

- 验证真实业务链路，而不只是接口层。

建议新增检查：

- KP 选中 NPC -> 玩家端回读可见
- KP 选中玩家席位 -> 玩家端回读可见
- KP 更新房间提示语 -> 玩家端回读可见

验收标准：

- 至少一条自动化用例覆盖“KP 推送 -> 玩家端消费”的闭环。

---

## 3. 推荐执行顺序

建议严格按下面顺序做：

1. `A1` 修内置模板同步
2. `A2` 收口同步失败文案
3. `B1` 补玩家席位展示
4. `C1` 修移动端遮挡
5. `B2` 梳理 KP 专用素材边界
6. `D1 + D2` 补自动化回归

原因：

- `A1` 不修，后面大多数联调都会被污染。
- `B1` 是用户能直接感知到的功能缺口。
- `C1` 和 `B2` 属于体验与信息架构优化，适合放在主链路恢复之后。
- 自动化应该跟着修复结果一起补上，否则问题会反复回归。

---

## 4. 完成定义

当下一阶段结束时，建议至少满足以下条件：

- 默认模组房间可正常同步地点 / NPC / 素材 / 玩家席位
- 玩家端能看到在场玩家
- 手机端玩家页首屏无遮挡
- KP 不会再看到原始 JS 异常
- smoke test 覆盖内置模板同步
- 至少一条联调用例覆盖 KP -> 玩家端闭环

---

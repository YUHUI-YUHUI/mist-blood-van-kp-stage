## 2. 已复现问题

### 2.1 P0：内置模板房间无法同步 KP 改动

#### 复现步骤

1. 打开首页，点击“我是 KP，创建雾中献血车”。
2. 进入 KP 页后，选中任意 NPC 或任意玩家席位。
3. 等待同步状态更新。

#### 实际现象

- KP 页顶部状态文案直接变成：

```text
Cannot read properties of undefined (reading 'map')
```

- 玩家端不会收到新的舞台状态。
- KP 页重新打开后，刚才的切换结果不会保留在服务端状态里。

#### 影响

- 当前所有基于内置模板创建的房间，核心实时联动能力基本不可用。
- 这会直接阻断“切换 NPC / 素材 / 玩家席位”的主流程。
- 首页默认入口看起来能创建房间，但实际无法完成带团流程。

#### 定位

- [server.mjs](/Users/yuhui/Documents/coc%20kp%20platform/server.mjs:495)
- [server.mjs](/Users/yuhui/Documents/coc%20kp%20platform/server.mjs:496)

`POST /api/rooms/:room/state` 的服务端逻辑里，内置模板分支使用了 `templateDefaults(room.state.templateId)`。  
但 `templateDefaults` 只包含 `initialStage` 和 `roomMeta`，不包含 `locations / npcs / materials / players`。  
随后代码又直接执行：

- `template.locations.map(...)`
- `template.npcs.map(...)`
- `template.materials.map(...)`
- `template.players.map(...)`

因此内置模板房间一旦推送状态就会在服务端抛错。

#### 修复建议

- 不要在服务端同步逻辑里继续使用只含默认值的 `templateDefaults(...)`。
- 服务端需要拿到一份完整的模板定义，至少要能访问：
  - `locations`
  - `npcs`
  - `materials`
  - `players`
  - `initialStage`
- 最稳妥的方向是统一“模板解析入口”，避免前后端各自维护一套半重复逻辑。

### 2.2 P1：玩家端完全不显示“在场玩家”

#### 复现步骤

1. 使用自定义模板创建房间，确保服务端同步本身可用。
2. 在 KP 页选中一个玩家席位。
3. 等待状态变为“舞台已同步”。
4. 打开对应玩家页。

#### 实际现象

- KP 预览区会正确显示玩家席位卡片。
- 玩家端不会出现任何玩家席位内容。
- 玩家页正文中也没有玩家名称或描述。

#### 影响

- README 与产品语义里都强调了“在场玩家 / 玩家席位”能力，但玩家实际看不到。
- 这会让 KP 端“切换在场玩家”的操作失去对玩家端的可见价值。

#### 定位

- [src/shared/stage/PlayerStage.tsx](/Users/yuhui/Documents/coc%20kp%20platform/src/shared/stage/PlayerStage.tsx:26)
- [src/shared/stage/PlayerStage.tsx](/Users/yuhui/Documents/coc%20kp%20platform/src/shared/stage/PlayerStage.tsx:119)

当前 `PlayerStage` 只渲染了：

- 场景背景
- 房间抬头
- NPC
- 素材
- 场景卡片
- 房间状态

但没有对应 KP 预览页里 `player-side / player-token` 的任何渲染逻辑。

#### 修复建议

- 给玩家端补齐玩家席位展示层。
- 最好与 [src/shared/stage/KpStagePreview.tsx](/Users/yuhui/Documents/coc%20kp%20platform/src/shared/stage/KpStagePreview.tsx:73) 的玩家区逻辑复用结构，而不是复制一套完全独立的实现。
- 同时补一条“KP 选中玩家席位 -> 玩家端可见”的联调用例。

### 2.3 P2：玩家端移动端状态徽章遮挡正文

#### 复现步骤

1. 打开玩家页。
2. 将视口切换到 `390 x 844`。

#### 实际现象

- `房间 XXXX · 已同步` 徽章会压在左上角文案卡片之上。
- 这会遮挡玩家提示语区域，导致正文阅读被打断。

本轮测得该重叠区域约为：

- 横向重叠：`161.96px`
- 纵向重叠：`33px`

#### 影响

- 手机端首屏信息层次被破坏。
- 玩家第一次打开房间时，最关键的说明文字会被覆盖。

#### 定位

- [src/pages/player/player.css](/Users/yuhui/Documents/coc%20kp%20platform/src/pages/player/player.css:21)
- [src/pages/player/player.css](/Users/yuhui/Documents/coc%20kp%20platform/src/pages/player/player.css:110)
- [src/shared/stage/stage.css](/Users/yuhui/Documents/coc%20kp%20platform/src/shared/stage/stage.css:54)

当前移动端样式中：

- `.stage-copy` 仍然占据左上大块区域
- `.room-indicator` 在 `max-width: 640px` 下被硬编码到 `top: 132px; right: 10px;`

两者没有做避让，导致实际重叠。

#### 修复建议

- 移动端把 `room-indicator` 移到更稳定的位置：
  - 顶部整行
  - 底部固定角标
  - 或直接并入 `stage-copy`
- 修复后需要补一次手机视口截图回归检查。

## 3. 可精进项

### 3.1 KP 专用素材与玩家可见素材缺少明确分层

当前 KP 素材列表中同时出现：

- 玩家手卡
- `KP 专用` 素材

但玩家端渲染使用的是公开素材分支，KP 端又没有把“切到这个素材后玩家是否可见”讲清楚。  
这会让 KP 在实际跑团时很容易误以为“已切换成功，玩家也能看到”。

建议：

- 直接把素材分成“玩家可见 / KP 专用”两个区块
- 或者对 `KP 专用` 卡片禁用“推送给玩家”的主操作
- 或者在卡片上明确显示“仅 KP 预览，不会出现在玩家端”

---

### 3.2 KP 端直接向用户暴露底层 JS 错误文案

本轮内置模板同步失败时，顶部状态直接显示：

```text
Cannot read properties of undefined (reading 'map')
```

这对开发排错有帮助，但对 KP 用户来说不可理解，也会破坏产品可信度。

建议：

- 前端统一把底层异常折叠成更可理解的提示
- 同时把原始异常留在控制台或日志上报链路里

---

### 3.3 现有 smoke test 没有覆盖“内置模板同步”主链路

当前本地 smoke 脚本已经覆盖了：

- 页面可打开
- 自定义模板建房
- 自定义模板状态推送
- 图片上传

但没有覆盖：

- 内置模板房间创建后再推送状态
- KP 选中 NPC / 玩家席位后，服务端状态是否正常更新
- 玩家端是否能看到对应变化

这也是为什么当前 P0 问题可以留到现在才暴露。

建议：

- 补一条内置模板同步用例
- 补一条 KP -> 玩家端的最小联调用例

---

## 4. 本轮结论

当前项目并不是“有很多零散小问题”，而是存在一个非常明确的主阻塞：

- **内置模板房间的状态同步链路已经断裂**

在这个主阻塞修复前，很多 UI 联调现象都会被它污染。  
因此下一步最合理的推进顺序应是：

1. 先修内置模板同步
2. 再补玩家席位在玩家端的展示
3. 再清移动端遮挡与信息架构问题
4. 最后补自动化回归
